案件3: 社内文書検索AI(RAG)

株式会社テックブリッジの社内文書(就業規則・経費精算マニュアル・情報セキュリティ規程・リモートワーク規程・ITアカウント申請ガイドの5本)を検索対象にして、質問に対して出典付きで回答するAIを構築した。

デモ画面(実際にテストした12問をチャット形式で再現): https://claude.ai/artifact/A1kWfq7ArV1KfmQ1wJcMpV

仕組み(アーキテクチャ)





取り込み(ingest.py): PDFからテキスト抽出 → 見出し単位でチャンキング(500〜1000字程度) → Embedding(数字の並びへの変換) → データベースへ保存



検索+回答生成(search_and_answer.py): 質問をEmbeddingに変換 → コサイン類似度で関連チャンクを検索 → Claude APIで出典付きの回答を生成(文書にない内容は「該当する情報が見つかりません」と回答するよう指示)



精度検証(run_tests.py): case3-test-questions.csv の12問で検証

設計と実際の実装が異なる点

当初の設計から、以下の点は作業環境の制約により変更している。正直に記録として残す。





Embeddingモデル: 本来はクラウドの多言語Embeddingモデルを使う想定だったが、作業環境のネットワーク制限でモデルのダウンロードができなかった。代わりに、文字n-gramのTF-IDF + SVD(次元圧縮)による手法で実装した。本番で使う場合はクラウドEmbeddingモデルへの差し替えが必要。



データベース(Supabase): pgvector拡張ありのテーブルは実際にSupabase上に作成済み(SQLも実行済み)だが、同じネットワーク制限でこの環境からは接続できなかった。検索・保存は環境内のローカルファイルで代替している。保存時のデータ形式はSupabase用のまま保持しているので、接続できる環境ではそのまま差し替えて使える。



Supabaseのリージョン: データ保管場所は国内(東京)を想定していたが、実際に作成したプロジェクトは選択ミスでSouth Asia(Mumbai)になっている。リージョンは作成後に変更できないため、本番運用前に東京リージョンでの再作成が必要。



チャットUI: Next.js + 認証を使った本番相当のUIは今回作らず、実際にテストした12問の結果を再現したデモ画面を作成した。新しい質問を自由に試せるライブ画面にするには、AIの処理を動かし続けるサーバーを別途構築する必要がある。



認証・セキュリティ: 本番用のAPIサーバーを構築していないため、「認証なしでAPIに直接アクセスできないか」のテストは今回未実施。

運用手順書

新しい文書を追加する手順





追加したいPDFファイルを文書フォルダに置く



ingest.py を実行する(既存のチャンク・Embeddingを再生成して保存し直す)



run_tests.py でテスト質問を流し、既存の正答率が落ちていないか確認する

本来は管理画面からアップロードできるようにする想定だが、今回は手動実行での追加手順とした。

Embedding再生成のタイミングとコスト

文書を追加・更新したときは、その文書だけでなく全チャンクを対象にEmbeddingを再生成する必要がある(今回の実装はTF-IDF+SVDという「全チャンクの単語の出現傾向」をもとにした方式のため、1文書を追加すると語彙全体の重み付けが変わり、既存チャンクのベクトルも影響を受ける)。本番でクラウドのEmbeddingモデルに差し替えた場合は、追加した文書分だけ再計算すればよく、文字数に応じた従量課金が発生する点に注意。

回答精度が落ちた時の調査手順





精度が落ちた質問を search_and_answer.py で単体実行し、検索結果の上位チャンクに正しい情報が含まれているか確認する



含まれていない場合は、チャンキング戦略(見出しでの分割ルール)を見直す。今回も「箇条書きの数字が見出しと誤認識される」という問題が実際に見つかり、検索件数を増やすことで対応した



正しいチャンクは取れているのに回答が外れている場合は、回答生成のプロンプト(SYSTEM_PROMPT)を見直す



最後に run_tests.py で全体の正答率を再測定し、他の質問への悪影響が出ていないか確認する
